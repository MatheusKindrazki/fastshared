## P0-1 — `site` aponta para um host que não existe

`web/astro.config.mjs:8` declara `site: 'https://www.fastsha.red'`. Esse host é **NXDOMAIN**:

```
$ dig +short www.fastsha.red A      → (vazio)
$ dig +short fastsha.red A          → 104.21.52.51 / 172.67.195.146
$ curl https://www.fastsha.red/og-image.png   → curl (6) Could not resolve host
$ curl https://fastsha.red/og-image.png       → 200
```

O `.claude/napkin.md` já registra isto desde 2026-04-26 ("App Store public URLs use apex domain —
`www.fastsha.red` has no DNS and fails precheck"). O site publicado ainda propaga o host morto.

**Blast radius medido no HTML em produção:**

| Consumidor | Valor publicado | Efeito |
|---|---|---|
| `og:image` / `twitter:image` | `https://www.fastsha.red/og-image.png` | **nenhuma pré-visualização de link tem imagem** — X, Slack, Discord, iMessage, LinkedIn |
| `og:url` | `https://www.fastsha.red/` | share aponta para host morto |
| `<link rel=canonical>` | `https://www.fastsha.red/` | a página se auto-descanonicaliza para um host que não resolve |
| `sitemap-0.xml` (todas as `<loc>`) | `https://www.fastsha.red/...` | crawler não busca |
| `robots.txt` → `Sitemap:` | `https://www.fastsha.red/sitemap.xml` | idem |
| JSON-LD `url` (`Base.astro:93`) | `https://www.fastsha.red` | idem |
| `/press` "Website" (`press.astro:116`) | link para `www.fastsha.red` | link morto na página feita para imprensa |

Isto atinge em cheio o público terciário descrito no `.impeccable.md` — "press, HN, Product Hunt
visitando na semana de lançamento" —, que chega justamente por link compartilhado.

**✅ Corrigido — e o escopo cresceu na verificação.** Trocar só o `astro.config.mjs` teria deixado
**dois** caminhos servindo o host morto, com todo o resto parecendo resolvido:

| Ponto | Por que a troca do `site` não bastava |
|---|---|
| `astro.config.mjs:8` | a raiz — alimenta `Astro.site`, o sitemap e as metatags |
| `Base.astro:20`, `:21` | fallbacks `Astro.site ?? '…'` — dormentes hoje, rearmam o bug se `site` sumir |
| **`Base.astro:93`** | **não é fallback: é literal incondicional** no JSON-LD, emitido em toda página |
| `press.astro:116` | **duas** ocorrências na mesma linha — o `href` **e** o texto âncora |
| `privacy.astro:339` | cópia visível na política de privacidade |
| **`public/robots.txt:4`** | **arquivo estático** — não é gerado, o build não o toca |

E o `robots.txt` tinha um **segundo defeito independente na mesma linha**: o caminho era
`/sitemap.xml`, que **não existe** (o `@astrojs/sitemap` emite `sitemap-index.xml`). Pior que 404 —
medido, `https://fastsha.red/sitemap.xml` responde **200 com `text/html`** (fallback do Pages), ou
seja, o crawler recebe uma página HTML anunciada como sitemap e nada acusa erro. A linha virou
`Sitemap: https://fastsha.red/sitemap-index.xml`.

**Evidência do build:** `www.fastsha.red` no `dist/` foi de **41 ocorrências em 9 arquivos → 0**.
Canonical, `og:url`, `og:image`, `twitter:image`, JSON-LD, robots e as 7 `<loc>` do sitemap, todos no
apex; os 6 canonicals das 6 páginas conferidos um a um.

⚠️ **`web/README.md:49` NÃO foi trocado mecanicamente, de propósito.** O texto instruía a anexar o
domínio `www.fastsha.red` ao Cloudflare Pages (passo que nunca foi executado — o NXDOMAIN prova) e,
na frase seguinte, dizia corretamente para **não** apontar o apex ao Pages. Uma troca ingênua
www→apex ali produziria a instrução exatamente errada e quebraria `/s/:token`, `/b/:token` e o
`apple-app-site-association`. A arquitetura real: o apex é custom domain do **Worker**
(`backend/wrangler.toml`), e `backend/src/index.ts` `routeRequest()` faz proxy de todo path não-app
para `fastshared-web.pages.dev`. O README foi reescrito para descrever isso.

Alternativa complementar (não substitui): criar o CNAME `www` → apex no Cloudflare, para que o host
deixe de ser um buraco.

## P0-2 — O CTA primário é invisível no tema escuro

`web/src/styles/global.css:203-213`:

```css
.btn-primary {
  background: var(--charcoal);   /* inverte:  #1d1d1f (light) → #f0f0f5 (dark) */
  color: #ffffff;                /* HARDCODED — não inverte */
}
```

O fundo usa o token semântico que vira; a cor do texto ficou fixa em branco. No tema escuro isso dá
**branco sobre quase-branco**. Medido por nó, em produção:

| Tema | background | color | contraste | AA (13px) |
|---|---|---|---|---|
| light | `rgb(29,29,31)` | `rgb(255,255,255)` | **16.83:1** | ✅ |
| **dark** | `rgb(240,240,245)` | `rgb(255,255,255)` | **1.14:1** | ❌ |

**Todos os CTAs de conversão do site usam `.btn-primary`:**

- `Hero.astro:61` — `JOIN TESTFLIGHT →` (o CTA principal da landing)
- `AgentCliSurface.astro:31` — instalação do CLI
- `pricing.astro:76, 95, 115` — `GO PRO →`, `GO PRO →`, `GO LIFETIME →` — **medidos os três em 1.14:1**

Ou seja: no tema escuro, o caminho inteiro de conversão e de monetização está ilegível. E escuro é o
default do público primário declarado no `.impeccable.md` ("macOS/iOS users who keep their OS in dark
mode").

**✅ Corrigido — mas NÃO da forma que este laudo propôs primeiro.** A proposta original era
`color: var(--cream)` + tinta escura fixa no `:hover`. A verificação adversarial derrubou as duas
metades, e recomputar a matemática derrubou também o remédio que ela sugeriu:

1. **Erro aritmético do laudo.** `#fbf8f1` sobre `#1d1d1f` é **15.87:1**, não 16.83:1 — este último
   é o número do `#ffffff`, reaproveitado por engano.
2. **A tinta fixa no hover cria um transiente no tema CLARO.** `global.css` transiciona
   `background` em 180ms mas **não** `color`. No claro o fundo sai de `#1d1d1f` (escuro) rumo a
   `#9d7aff` (claro); com a tinta saltando para escuro em t=0 dá **1.14:1**, com 146ms abaixo de 4.5.
   Trocaria uma falha permanente no escuro por uma transitória no claro.
3. **Pôr `color` no `transition` é PIOR, não melhor.** Se as duas propriedades interpolam juntas, o
   texto **cruza** o fundo: medido em varredura de 1000 amostras, **1.00:1 em t=0.63** — o rótulo
   desaparece por completo no meio da animação. (Foi o remédio sugerido pela verificação; a conta o
   refuta.)

A impossibilidade é estrutural: nenhuma cor única serve aos dois extremos da rampa. Para ≥4.5:1
contra `#1d1d1f` a tinta precisa de L ≥ 0.233; contra `#9d7aff` (L=0.283) uma tinta assim rende
1.18:1. **Logo o remédio tem de ser a SUPERFÍCIE, não a tinta.**

O que foi entregue: um token de superfície de acento que **inverte junto com `--charcoal`**, para
que os dois extremos da rampa fiquem sempre do mesmo lado da divisa de luminância.

```css
:root              { --accent-surface: #3b1f86; }  /* claro: violeta profundo, pede texto claro  */
[data-theme=dark]  { --accent-surface: #9d7aff; }  /* escuro: violeta hot,   pede texto escuro  */

.btn-primary        { background: var(--charcoal); color: var(--cream); }
.btn-primary:hover  { background: var(--accent-surface); }
```

`#3b1f86` não é cor nova — é o `violet.DEFAULT` / `deep-violet` que já existe no
`tailwind.config.mjs`; o que se acrescentou foi o nome semântico pareado.

**Medido no build, por nó, nos dois temas** (e a rampa de hover varrida em 1000 amostras):

| | repouso | hover | pior ponto da rampa |
|---|---|---|---|
| claro | **15.87** ✅ | **11.47** ✅ | **11.47** ✅ |
| escuro | **16.85** ✅ | **6.07** ✅ | **6.07** ✅ |

Os 4 estados estáveis passam e **as duas rampas inteiras passam** — o `color` nunca muda, então não
há cruzamento. Os três CTAs de `/pricing` foram de **1.14 → 16.85**.

**Regressão: zero, verificada contra baseline.** Varredura WCAG por nó da home inteira:
escuro **4 → 2 falhas** (as duas do CTA sumiram; sobraram duas pré-existentes no chip do mockup);
claro **10 → 10**, com ratios idênticos aos medidos no código não modificado em produção — nenhuma
delas é `.btn-primary`.

## P1-3 — A OG image está inalcançável **e** fora do sistema visual

Além de não resolver (P0-1), o arquivo em si diverge do site atual. `pixel_audit.py`:

| | OG image | site (dark) | site (light) | alvo |
|---|---|---|---|---|
| luminância | 37.99 | 25.85 | 238.2 | <60 ou >200 |
| **saturação** | **0.584** | 0.099 | 0.045 | **≤0.15** |
| contraste std | 35.99 | — | — | ≥40 |
| fundo dominante | **8.6%** (gradiente) | 86% | 86% | **≥80%** |

A OG é a identidade **roxa antiga** (gradiente violeta, saturação 0.58). O site vivo é neutro
(`#0f0f12` / `#fbf8f1`, saturação 0.10 / 0.045). Quem vê o card e clica encontra outra marca.

Contra a receita padrão do corpus (OGFolio, censo de 896 itens — 75% `Typography`):

- ❌ **sem tagline.** Só wordmark + tile do ícone. A linha que faz a persuasão inteira do produto —
  *"Share anything. Get a link. Watch it vanish."* — não está lá. Na miniatura do feed, o tipo é o
  que sobrevive; hoje ele não diz nada.
- ❌ **sem prova de produto.** ~45% das instâncias de tag do OGFolio são screenshot/mockup. O site já
  tem o fragmento perfeito pronto: o *transfer manifest* com `410 Gone`.
- ❌ **fundo dominante 8.6%** — o gradiente impede qualquer chão sólido ≥80%.
- ⚠️ contraste 35.99, abaixo do piso operacional 40 (embora dentro do ~35 que o OGFolio observa nas
  amostras fortes).

**Correção:** regerar 1200×630 sobre chão sólido `#0f0f12` (≥85% da área), wordmark + a tagline em
Bricolage, o manifest com `410 Gone` como prova, violet-hot em um só ponto. O `.impeccable.md:118` já
lista "regenerate `public/og-image.png`" como thread aberta desde abril — continua aberta, e agora com
o agravante de estar publicada num host morto.

## P1-4 — O documento de direção contradiz o código publicado

`.impeccable.md` se declara "the single source of truth for design decisions" (última atualização
**2026-04-19**). Dois pontos load-bearing morreram desde então:

| `.impeccable.md` diz | O código faz |
|---|---|
| "**Theme: dark.** Light mode for the marketing site is **explicitly out of scope**. **Do not propose a toggle.**" | `:root` é **light** (`--cream #fbf8f1`); dark vem de `[data-theme="dark"]`; **existe um toggle** em `Nav.astro:120-135`; default segue `prefers-color-scheme` (`Base.astro:33`) |
| Paleta: `--ink #070318` + dois glows radiais roxo/rosa | Paleta neutra tipo Apple: `--cream #fbf8f1`/`#0f0f12`, `--charcoal #1d1d1f`, `--silver #6e6e73`, `--tin #a1a1a6`. Medido: saturação 0.045–0.10, dominante acromática 86% |

Não estou questionando as decisões — as duas parecem deliberadas e o resultado medido é bom. O
problema é de governança: **a próxima execução de `/impeccable` (ou desta skill) vai projetar contra um
sistema que não existe mais**, e o `.impeccable.md` instrui explicitamente a "não redefinir, só
consumir" tokens que foram substituídos.

**Correção:** atualizar `.impeccable.md` — seção *Aesthetic Direction* (paleta real, dois polos,
toggle) e *Out of Scope* (remover "light mode decidido fora"). Foi isto que permitiu a OG image ficar
órfã por 4 meses.

## P2-5 — O contraste desaba depois do hero

Piso operacional: **std ≥40 em áreas de texto**. Medido por recorte de faixa, em produção:

| Região | dark | light |
|---|---|---|
| hero (headline + manifest) | **43.3** ✅ | **42.5** ✅ |
| promise-band | 26.9 ❌ | — |
| rodapé | 29.5 ❌ | 29.5 ❌ |
| página inteira | 26.6 | 26.4 |

O hero passa com folga; tudo depois dele achata. A causa é estrutural: das **7 `<section>`** da
landing, só **uma** (`promise-band`, `rgb(11,6,27)`) tem fundo próprio — as outras seis são
transparentes sobre o mesmo chão. Sem alternância, não há ritmo.

É exatamente o mecanismo que o corpus mede: no Framer o contraste de 85–93 entre terços **vem** da
alternância dark/light entre seções; no Linear a densidade cai de 3.1% → 1.8% rumo ao rodapé de forma
deliberada. Aqui a queda não é ritmo, é uniformidade.

**Correção:** alternar `--cream` ↔ `--canvas`/`--surface-warm` por seção. Os tokens já existem nos dois
temas e a alternância funciona nos dois polos — o argumento "só temos dark" que justificava a
uniformidade deixou de valer quando o toggle entrou (P1-4).

## P2-6 — O rodapé é faixa legal (anti-padrão #6)

Medido: **149px** de altura numa página de 5507px, **5 links** em linha única, sem agrupamento, sem
CTA, sem newsletter:

```
fastshared.  2026        PRESS  SUPPORT  PRIVACY  TERMS  GITHUB ↗
```

Não é nenhum dos três arquétipos do footer.design (695 itens curados, 36 styles, motion de 1ª classe):
não é multi-coluna SaaS, não é link-list vertical editorial, não é statement tipográfico gigante.

**Correção:** o arquétipo on-brand aqui é o **giant typographic statement** — o rodapé como última cena
da marca. É a única superfície da página onde "watch it vanish" pode ser encenado em vez de descrito,
e resolve de quebra o P2-5 (a última zona ganharia contraste próprio) e o final abrupto da página.

✅ **Validado nos dois lados** (a galeria exige dupla captura): desktop 1440 e mobile 320/390/430/768.

## O que está forte — não mexer

Medições, não impressão:

- **Disciplina de polo (traço #1 do DNA).** dark lum **25.85** / light lum **238.2**. Zero cinza médio.
  O light bate quase exatamente as referências claras do SaaSpo (lum ~240–245).
- **Saturação de base.** 0.099 (dark) e **0.045** (light), contra alvo ≤0.15. O light é mais contido
  que 5 dos 6 exemplos do posts.design.
- **Um neutro dominante.** `#111113` a 86% / `#faf7ef` a 86% — acima do piso ≥80%.
- **Um acento, com papel funcional.** `--violet-hot` aparece como sublinhado de "vanish", estado
  `410 Gone` e `+` do FAQ. Nunca como decoração. É o padrão "1% de cor" do LogoInspo.
- **Tipografia como identidade.** Bricolage Grotesque + JetBrains Mono, tracking agressivo, mono
  all-caps reservado a rótulo/número. Sem terceira face.
- **Produto como prova.** O *transfer manifest* (`screen-recording.mov` · `23 h 59 min` · `410 Gone`) é
  fragmento de UI em escala real — o registro Things 3 / Linear que o `.impeccable.md` mira, e acertou.
  `410 Gone` é o melhor detalhe da página: a efemeridade vira estado de dado, não adjetivo.
- **Conteúdo largo rola no próprio contêiner.** `.agent-terminal pre { overflow-x: auto }` — o `<code>`
  que ultrapassa 390px rola dentro do bloco, sem quebrar a página. Correto.
- **Sem overflow horizontal de página** em 320/390/430/768 (`scrollWidth == clientWidth` nos quatro).

## Observação com ressalva — densidade

`edge_density`: hero **0.094**, página inteira **0.120**. Acima de toda referência de landing medida
no corpus (Vercel 2.5%, Linear 3.1%→1.8%, Notion 7.1% — o mais denso da amostra clara).

A assinatura é visível: muitos fios de 1px (linhas do manifest, divisores da faixa de stats,
separadores do FAQ). Não chamo de defeito — é escolha estética coerente com o registro "engenharia
precisa", e casa com a tese de "prova por abundância" do Notion.

⚠️ **Ressalva metodológica:** as métricas da galeria vêm de capturas de frame único; 0.120 aqui é
medido sobre uma costura full-page de 5507px, o que infla a comparação. Os dois números não são
diretamente comparáveis. Trate como sinal, não veredito.

### P2-7 — `--violet-hot` como texto não sobrevive ao tema claro (achado na verificação)

A varredura WCAG por nó expôs 10 ocorrências no tema **claro** onde `--violet-hot` (`#9d7aff`) é usado
como **cor de texto** sobre o fundo cream: **2.97:1**, abaixo de AA. São justamente os rótulos que
carregam a identidade — `FLOW`, `01`/`02`/`03`, `APPLE-NATIVE`, `AGENTS + CLI`, `LIVE ACTIVITY`,
`QUESTIONS` e o **`410 Gone`**, o melhor detalhe da página.

Não é regressão — está assim no código publicado, e é **simétrico** ao P0-2: `--violet-hot` é um
violeta claro, ótimo como texto sobre escuro e insuficiente sobre cream. O conserto é o mesmo padrão
que este PR introduziu: um token de **tinta** de acento que inverta (violeta profundo no claro,
violeta hot no escuro), em vez de uma cor fixa nos dois temas.

## Proveniência e limites

- Heurísticas: dossiê `design-intelligence-deepsearch-v2` (2026-08-14) — 8 galerias, 193 amostras, 46
  análises pixel-quantitativas. Qualificadores obrigatórios ao citar: **SaaSpo n=5** (Wayback,
  mar–jun/2026), **posts.design n=24** (10–14/08/2026), **LogoInspo dark canvas n=6**. Censos citáveis
  sem ressalva: OGFolio 896, footer.design 695, Deck Gallery 179.
- Referências usadas **como padrão, nunca como pixel** — nenhum layout, paleta ou composição copiado.
- `pixel_audit.py` é quantitativo, não perceptual. Luminância, contraste (desvio-padrão), saturação,
  densidade de bordas e cores dominantes são medidas reais; leituras de composição estão marcadas.
- Contraste WCAG foi **computado por nó** (cor efetiva vs. fundo efetivo subindo a árvore), não
  estimado visualmente.
- **Correção registrada:** uma primeira captura em Chrome headless a 390px sugeriu overflow horizontal
  no mobile. Era artefato — headless sem emulação de viewport renderiza layout desktop numa janela
  estreita. A medição correta (iframe same-origin em 4 larguras) mostra `scrollWidth == clientWidth`
  nas quatro. **Não há bug de overflow mobile.**
- Não auditado: app Apple (SwiftUI), `/press`, `/privacy`, `/terms`, `/support`, e o comportamento de
  motion (`prefers-reduced-motion`).
